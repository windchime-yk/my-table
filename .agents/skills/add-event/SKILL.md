# イベントを追加する

公式のタイムテーブルから `events/<event-id>.json` を作り、整合チェックを通して PR にする。

決まりの定義元は [docs/SPEC.md](../../../docs/SPEC.md) の「イベントデータ」。この Skill は手順をまとめたもので、迷ったら SPEC を読む。項目の一覧は SPEC の「スキーマ（v1）」、定義は `schema/v1/event.ts`。

## 1. 材料をそろえる

次のものを受け取る。足りないものは、ファイルを作る前にまとめて聞き、返事を待つ。スキーマで省略できる会場や公式サイトの URL も一度は聞き、「ない」「分からない」と言われたら `null` にする。`visibility` だけは、返事がなければ `private` で進めてよい。

- 公式のタイムテーブル。日ごと・ステージごとに全部。受け取り方は下の表のどれでもよい
- イベント名、会場、開催日、公式サイトの URL
- タイムゾーン（日本のイベントなら `Asia/Tokyo`）
- 公開してよいか（`visibility`）。分からなければ `private` で作り、公開は依頼した人に決めてもらう

タイムテーブルの受け取り方と読み方:

| 受け取り方                             | 読み方                                                                                                                             |
| -------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| 画像（スクリーンショット・写真）       | 画像を読んで書き起こす。文字が小さい・つぶれているところは推測せず、4. で確かめる                                                  |
| PDF                                    | 文字を読み取れればそのまま使う。画像だけの PDF は、画像と同じように読む                                                            |
| Web ページの URL                       | ページを取得して読む。取得できない（ログインが要る・スクリプトで描画される）ときは、ページの本文かスクリーンショットを貼ってもらう |
| 貼り付けたテキスト（告知・投稿の文面） | そのまま読む。どこから写したか（公式サイト・公式の投稿など）を聞いて、`event.sources` に書く                                       |

材料が複数あって食い違うとき（画像と Web ページで時刻が違うなど）は、どちらかに決めつけず、食い違う箇所を挙げて確かめる。

## 2. イベントID を決める

- 英小文字・数字・ハイフンだけ。例: `example-fes-2026`
- ファイル名は `events/<イベントID>.json`。URL は `/e/<イベントID>` になる
- 一度公開したら変えない

## 3. データを組み立てる

イベント → 日 → ステージ → 枠 の4階層で書く。`scripts/lib/fixtures/events/example-fes-2026.json` が、ひととおりの項目を使った見本になる。

```json
{
  "$schema": "https://mt.whyk.dev/schema/v1/event.schema.json",
  "schema_version": "1",
  "id": "example-fes-2026",
  "visibility": "private",
  "event": {
    "name": "Example Fes 2026",
    "venue": "Example Hall",
    "timezone": "Asia/Tokyo",
    "official_url": "https://example.com/",
    "sources": ["公式タイムテーブル画像（DAY1 12/05）"]
  },
  "days": [
    {
      "date": "2026-12-05",
      "label": "DAY1",
      "stages": [
        {
          "id": "main",
          "name": "Main STAGE",
          "slots": [
            {
              "id": "d1-main-1230",
              "start": "12:30",
              "end": "13:00",
              "end_source": "next_slot",
              "title": "Artist A",
              "kind_label": "LIVE",
              "category": "performance"
            }
          ]
        }
      ]
    }
  ]
}
```

守ること:

- **事実だけを取り込む。** 時刻・ステージ・出演者名・タイトル・公式の表記（`LIVE` など）まで。トークの概要文、登壇者のアイコン、アーティスト写真、公式画像そのものは取り込まない
- **時刻**は、イベントのタイムゾーンでの `HH:MM`。日をまたぐ深夜帯は `24:30` のように24時以降で書き、その日の枠として入れる
- **枠の `id`** は、公式の ID があればそれを使う。なければ `d1-main-1230`（何日目・ステージ・開始時刻）の形で振る。イベントの中で重複させない（`items` の `id` とも重複させない）
- **`title`** は、音楽系なら出演者名、カンファレンスならトークのタイトル
- **`end_source`**（終了時刻の根拠）は正直に付ける。`explicit` にするのは、公式に終了時刻が書いてあるときだけ。推定の終了時刻は画面に出ない
  - `explicit`: 公式に終了時刻が書いてある
  - `next_slot`: 次の枠の開始時刻を終了時刻にした
  - `inferred`: 前後から推定した
  - `day_end`: 終演時刻から決めた
- **ステージの `id`** は、その日の中で重複させない。並び順が画面の並び順になる
- **ステージの色**（`color`）は省略してよい。指定するなら OKLCH で書く（例: `oklch(70% 0.15 30)`）
- **取り込み元**（`event.sources`）に、何を見て作ったかを書く（例: `公式タイムテーブル画像（DAY1 12/05）`）

タイムテーブルの形に応じて使う項目:

| タイムテーブルの形                                      | 書き方                                                                                      |
| ------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| 開場・休憩・懇親会など、選ぶ対象でない時間帯            | 日の `day_events` に書く。特定のステージだけなら `stages` にステージの `id` を入れる        |
| 1つの枠に、個別の開始時刻なしで複数のトークが入っている | 枠の `items` にトークを順に書く。枠の `title` は `null` にでき、`kind_label` が見出しになる |
| ほかのステージに同時中継される                          | 元の枠の `simulcast_in` に、中継先のステージの `id` を入れる。枠は増やさない                |
| ステージが閉まっている時間帯                            | ステージの `closed` に `[{ "start", "end" }]` で書く                                        |
| 「撮影禁止」などの印                                    | `tag_definitions` にキーと表示名を定義し、枠の `tags` にキーを入れる                        |

## 4. 読み取れないところは聞く

画像がつぶれて読めない出演者名、判別できない時刻、どのステージか分からない枠は、推測で埋めない。該当の箇所を挙げて、依頼した人に確かめる。

## 5. 整合チェックを通す

```sh
pnpm validate events/<イベントID>.json
```

- `✗` はエラー。直すまで先に進まない。よくあるものは、`id` の重複、同じステージでの時間の重なり、終了時刻が開始時刻以前、定義していないタグ
- `⚠` は警告。枠と休憩などの時間が重なっているときに出る。公式の表記どおりなら直さず、そのまま報告する
- 仕上げに `pnpm fmt` で整形する

## 6. 画面で確かめる

```sh
pnpm dev
```

`/e/<イベントID>` を開いて、公式のタイムテーブルと見比べる。`events/` にファイルを足したときは、開発サーバーを立ち上げ直す。`private` のイベントは画面に出ないので、確かめる間だけ `public` にしてよい（コミットする前に戻す）。

## 7. PR にする

- ブランチは `chore/…`、タイトルは `chore: add <イベント名> event data`。データの追加で、機能は変わらないため。そのほかの決まりは [AGENTS.md](../../../AGENTS.md) の「作業の進め方」
- `public` のイベントは、main にマージすると本番に出る

## 8. 報告する

- 何日分・何ステージ・何枠を入れたか
- `explicit` 以外の終了時刻の枠数を、`end_source` ごとに（例: `next_slot` 2枠、`inferred` 1枠）。推定した時刻はその根拠も
- 読み取れずに確かめた箇所、警告の内容
- `visibility` をどちらにしたか
