# イベントのデータを更新する

公式の告知に合わせて `events/<event-id>.json` を直し、整合チェックを通して PR にする。開催当日の変更も、同じ手順で反映する。

決まりの定義元は [docs/SPEC.md](../../../docs/SPEC.md) の「データ作成の指針」。この Skill は手順をまとめたもので、迷ったら SPEC を読む。

## いちばん大事な決まり

**枠の `id` は変えない。** 利用者のマイテーブルは、この `id` で保存されている。時刻やステージが変わっても同じ `id` のままにすれば、利用者の選択はそのまま残る。`id` を変えると、選んでいた人のマイテーブルからその枠が外れる。

## 1. 変更の内容を確かめる

- 公式の告知（URL・画像・投稿）と、その日時を受け取る
- どの日の、どのステージの、どの枠が、どう変わるのかを、告知から読み取る。読み取れないところは推測せず、依頼した人に確かめる

## 2. 変更の種類ごとに直す

| 変更                                     | 書き方                                                                                                       |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| 押し（遅延）                             | まだ始まっていない枠の時刻をずらす。`note` に根拠を残す（例: `20分押し（公式告知 11/01 18:31）`）            |
| 時刻・ステージの変更                     | 時刻を直す。ステージが変わるなら、枠をそのステージの `slots` に移す                                          |
| 枠の追加                                 | 新しい `id` の枠を足す                                                                                       |
| リトライ（機材トラブルなどでのやり直し） | 元の枠は残し、やり直しの枠を新しい `id` で足す。`note` にリトライである旨を書く                              |
| キャンセル                               | 枠を削除する。後ろの枠が繰り上がるときは、その枠の時刻を直す（消さずに残すと、繰り上がった枠と時間が重なる） |

あわせて直すところ:

- すでに終わった枠の時刻は、さかのぼって直さない
- 時刻をずらしたら、`end_source` が今も正しいかを見る。公式が新しい終了時刻を書いていなければ、`explicit` のままにしない
- `event.sources` に、根拠にした告知を足す（例: `公式告知「Night STAGE 20分押し」（11/01 18:31）`）
- 公式に書かれていない事情や理由は書かない。取り込むのは事実だけ

## 3. 整合チェックを通す

```sh
pnpm validate events/<イベントID>.json
```

時刻をずらしたあとは、同じステージの前後の枠と時間が重なりやすい。`✗`（エラー）が出たら、ずらし忘れた枠がないかを見る。仕上げに `pnpm fmt` で整形する。

## 4. PR にする

- ブランチは `fix/…`、タイトルは `fix: update <イベント名> timetable`。そのほかの決まりは [AGENTS.md](../../../AGENTS.md) の「作業の進め方」
- main にマージすると、本番に反映される。当日の変更は、利用者が見ている最中に反映されるので、マージの前に差分を見直す

## 5. 報告する

- どの枠を、どう直したか（`id` と、変更前後の時刻）
- 削除した枠があれば、その `id`。選んでいた利用者には、次に開いたときに「選んでいた N 件が外れました」と出る
- 根拠にした告知と、その日時
